# FERA security baseline

Generated from `fera.security.policy` (fera_baseline 1.0.0) by `scripts/generate_security_policy_docs.py`.
Do not edit this file by hand: change the tables and regenerate it.

```
python scripts/generate_security_policy_docs.py
```

Everything below is data the assessment engine reads at run time.  The same tables travel inside every report (`policy_id` plus the rule ids that were applied), so a report can always be traced back to the baseline that scored it.

## How a score is computed

```
100 - sum(min(category_total, weight * 100))
```

with, for each finding,

```
base_points * status_factor * evidence_factor
```

and the following guarantees:

- one finding per (rule_id, dedup_key): the most expensive one
- one finding per property_key pays: the most severe one decides
- a category deduction is capped at weight * 100
- NOT_VERIFIABLE never deducts and never counts as coverage

### Encryption transforms

| transform | tier | strength (bits) | why |
| --- | --- | --- | --- |
| `ENCR_AES_GCM_16` | RECOMMENDED | 128 | AES-GCM with a 128-bit ICV encrypts and authenticates in one transform; the full-length tag keeps a forgery attempt near 2^-128 |
| `ENCR_AES_GCM_12` | ACCEPTABLE | 96 | AES-GCM with a 96-bit ICV: the cipher is fine, the shorter tag moves the forgery bound to roughly 2^-96 |
| `ENCR_AES_GCM_8` | DEPRECATED | 64 | AES-GCM with a 64-bit ICV: a birthday-bound forgery effort near 2^32 packets is reachable on a busy tunnel, which is also why the truncated tag is the one place ESP's integrity stops being free |
| `ENCR_CHACHA20_POLY1305` | RECOMMENDED | 128 | AEAD with a 128-bit tag and no hardware dependency; the preferred choice on endpoints without AES instructions |
| `ENCR_AES_CBC` | ACCEPTABLE | 128 | AES-CBC provides confidentiality only, so a separate integrity transform is mandatory; padding oracles such as Lucky13 are mitigated, not designed away |
| `ENCR_3DES` | DEPRECATED | 112 | 3DES has a 64-bit block, so a birthday collision appears after a few million packets and turns the tunnel into a Sweet32-style ciphertext sampling problem; effective strength is 112 bits, not 168 |
| `ENCR_DES` | FORBIDDEN | 56 | Single-DES has a 56-bit key, exhaustible with dedicated hardware, and a 64-bit block |
| `ENCR_DES_IV64` | FORBIDDEN | 56 | A 64-bit initialisation-vector variant of single-DES, so the same 56-bit key |
| `ENCR_NULL` | FORBIDDEN | 0 | NULL encryption leaves the payload in clear text; it exists for authentication-only testing and must never carry user traffic |

| transform | tier | strength (bits) | why |
| --- | --- | --- | --- |
| `CURVE25519` | RECOMMENDED | 128 | Curve25519: 128-bit strength, constant-time implementations are the norm and the group has no small-subgroup traps |
| `ECP_256` | RECOMMENDED | 128 | NIST P-256: the cheapest group that reaches the 128-bit target |
| `ECP_384` | RECOMMENDED | 192 | NIST P-384: 192-bit strength, the pairing this baseline gives AES-256 |

| `MODP_6144` | RECOMMENDED | 152 | MODP-6144: well above the target |

## SA lifetimes

**IKE SA**: target 28800s, accepted up to 86400s, maximum 604800s. an IKE SA key protects every child SA derived from it, so one day is the most exposure this baseline accepts and eight hours is the target

**Child SA**: target 1800s, accepted up to 3600s, maximum 86400s. a child SA key protects the bulk data flow, so the window in which a compromised key decrypts traffic should be minutes, not days
